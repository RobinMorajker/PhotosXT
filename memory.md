# Memory — PhotosXT

Durable facts and decisions that a future session would otherwise have to rediscover. One line each; delete a line when it stops being true. Status and in-progress work belong in `.session/` logs, not here.

## Decisions
- App name is **PhotoXT**; the folder and the Claude project are named PhotosXT.
- Stack: native Android, Kotlin + Jetpack Compose (chosen over Kotlin Multiplatform and Flutter, 2026-11-04).
- Audience: private first (family, up to 100 Google accounts), kept Play Store-ready for a later public launch (2026-11-04).
- SDK levels: minSdk 30 (Android 11), targetSdk and compileSdk 37 (Android 17). Google Play requires target 36+ since 31 Aug 2026.
- Backend: Firebase in asia-south1 (Auth, Firestore, Functions, Hosting, Storage, FCM, App Check). It is used only for public albums, boards, share-link records and invites.
- Drive scopes: `drive.readonly` when the first folder is added, upgrade to `drive` on the first write, `drive.appdata` for settings sync. `drive.file` + Google Picker can't list a picked folder's contents: re-tested in the Phase 3 spike (2026-11-06), the picked folder itself is readable but 0 of its 2,001 children are listed.
- Data boundary: Drive content, Drive metadata and OAuth tokens never leave the device. Why: restricted-scope data stored on or sent to servers triggers Google's yearly security assessment.
- Sharing with people uses Drive permissions; the Shared Albums "With me" view reads Drive `sharedWithMe`. Links are Android App Links on the Firebase Hosting domain (Firebase Dynamic Links shut down in Aug 2025).
- Google Cloud for private use: in Testing status, grants expire every 7 days. In production but unverified, users see a warning and the project is capped at 100 users.
- Two editions (2026-11-04): PhotoXTPro is the full spec, including public media boards. PhotoXT is the same spec without media boards; Public Albums stay, since only boards were asked to go. Section and phase numbers match in both specs.
- One codebase for both editions (Robin, 2026-11-04). Build PhotoXT now; add the `pro` product flavor (PhotoXTPro) in this repo when board work starts (Phase 12). No flavors before that.
- Git and CI (Robin, 2026-11-04): this folder is the repo root, branch `main`. The remote `origin` is github.com/RobinMorajker/PhotosXT (Phase 0 pushed by Robin). CI is `.github/workflows/ci.yml` and runs on every push to `main`; the same command runs locally (see README "Build and check"). Sessions commit locally; Robin pushes.
- Toolchain (pinned 2026-11-04 in `gradle/libs.versions.toml`): Gradle 9.8.2, AGP 9.5.0 with built-in Kotlin (never apply `org.jetbrains.kotlin.android`), Kotlin 2.4.21, KSP 2.3.13, Hilt 2.60.1, Compose BOM 2026.09.00 (Material 3 1.4.0), Navigation 3 1.2.0. Builds need JDK 17+; CI uses 21.
- `applicationId` and namespace are the placeholder `com.photoxt.app` until open decision 1 (spec §9) is settled, before Phase 11.
- Navigation: one Navigation 3 back stack per tab, each with its own saveable-state and ViewModel-store decorators, so a tab keeps its state and ViewModels while hidden (nav3-recipes "multiple back stacks"). Back exits through Pictures. An album opens as `AlbumKey` on the Albums stack.
- One UI header: `PxtCollapsingHeader` in core/designsystem on Material 3's exit-until-collapsed scroll behaviour. Expanded = 40% of the window height, collapsed = 64 dp, and no expansion on windows under 480 dp tall. A bottom toolbar row holds the navigation icon, actions and the collapsed title; every header carries the test tag `PXT_HEADER_TEST_TAG`.
- Logging: only `PxtLog` (core/common). It redacts tokens, e-mails, URIs, paths, media file names and coordinates; debug StrictMode reports through it.
- No Android cloud backup or device-to-device transfer (`allowBackup`/`fullBackupContent` false, `data_extraction_rules.xml` excludes everything). Settings restore through the user's Drive app-data folder (spec §4.8) instead.
- Theme: dynamic colour by default; without it, the Material 3 baseline scheme until the accent setting exists (§4.20). AMOLED black is `PxtTheme(amoledBlack = true)` and gets a user setting with the other theme options.
- Icons: Material Symbols Rounded, as vector drawables in core/designsystem (`ic_tab_*`). Not `material-icons-extended`.
- `baselineprofile/` holds both the Baseline Profile generator and the Macrobenchmark startup test (Android Studio's layout); there is no separate `benchmark/` module.
- Quality gates run from the root: Spotless with ktlint `android_studio` style (100 columns, no trailing commas), detekt 1.23.8, and Android Lint with warnings as errors (version-age checks and `ObsoleteLintCustomCheck` disabled).
- Modules added in Phase 1: `core/model` (plain Kotlin types; uses the Android library convention, no Android APIs), `core/database` (Room), `core/media` (MediaStore indexer, access, thumbnails), `feature/timeline` (Pictures and the grid of one album) and `feature/albums`. Hilt modules use the `photoxt.android.hilt` convention plugin.
- Room v1 (Phase 1): `album`, `media` and `media_store_cursor` (per volume: MediaStore version, generation and the time zone of the day keys). Schemas are exported to `core/database/schemas`; every later version needs a migration test.
- Ids: device media `device:<MediaStore _ID>`, device albums `device:<BUCKET_ID>`. `media.dayKey` and `monthKey` are local-calendar keys of `takenAt` (epoch day; year*12+month-1), so SQL can group; a time-zone change rescans.
- Timeline rows come from one UNION query (each date header, then its items) paged by Room with placeholders and jumps, so headers sit at exact positions. `TimelineLayout` (core/ui) is built from the same query's group counts: placeholder spans, fast-scroller labels, select-all counts, and keeping the same photo in view when the grouping changes.
- Pinch density, densest first: year (12 columns), month (9), then days at 7 down to 1 columns; default 4. Wider windows multiply the columns per 360 dp. Kept in saved state only; it persists with Settings (Phase 6).
- MediaStore indexer: per volume, a generation scan of changed items. An id diff (deletions, plus a direct fetch of ids Room has never seen) runs on every return to the foreground, after permission answers and on MediaStore delete notifications; insert and edit notifications skip it. Full rescans only on a new MediaStore version or time zone. A failed query throws instead of looking like "nothing there".
- Device thumbnails: MediaStore's own thumbnail (`openTypedAssetFile` with `EXTRA_SIZE`), decoded by Coil at tile size into software bitmaps; at most 4 provider reads at a time. Nothing is written to PhotoXT's storage. Hardware bitmaps are off in the app's image loader because they made grid scrolling worse on the A15 (see Known limits); a full-size viewer image may opt back in per request.
- Grid gestures live on the grid, not the tiles: tap, long-press, drag-select with edge auto-scroll, and pinch. Tiles only declare semantics (TalkBack open, select, toggle). While selecting, the navigation bar hides and the selection action bar takes its place.
- Selection is a map of id to capture time in the ViewModel (not saved across process death). Share hands up to 500 items to the system share sheet.
- Permissions: READ_EXTERNAL_STORAGE up to API 32, READ_MEDIA_IMAGES/VIDEO from 33, plus READ_MEDIA_VISUAL_USER_SELECTED from 34. Limited access shows a banner with Manage (picker) and Allow all (app settings), because on One UI 8 asking again only offers the picker.
- detekt: LongParameterList ignores composables, MagicNumber ignores enums. Lint wants `toUri()`, so core-ktx is an explicit dependency.
- Tests: Robolectric runs Android 17, which needs `--add-opens java.base/jdk.internal.access` (set in build-logic) and espresso-core 3.7+ (pinned in app). Screenshot goldens live in `app/src/test/screenshots`; re-record with `./gradlew recordRoborazziDebug`. Screenshot tests click with semantics actions, because touch ripples differ between runs.
- Modules added in Phase 2: `feature/viewer` (pager, compare, slideshow, 360° view, details sheet) and `feature/player` (Media3). Libraries, all §5.1: Telephoto 0.19 (zoomable-image-coil3), Media3 1.11 (exoplayer, session, ui-compose), ExifInterface, coil-gif, Maps Compose 9, room-testing.
- Full-screen destinations (viewer, player, compare, slideshow, 360°) sit on one overlay back stack above the tabs (`app/Overlays.kt`), so the grid stays drawn under the viewer while it is swiped down. A covered overlay is not drawn and is hidden from TalkBack but keeps its state.
- Grid ↔ viewer transition: a hand-made flight (`MediaHero`, `HeroTiles` in core/ui) from the tapped tile's bounds, not `SharedTransitionLayout`, which would put the whole app and every grid scroll inside a lookahead scope. The tile hides while its photo flies; on close the grid scrolls the current item into view first. After process death the viewer fades in instead.
- The viewer pages the grid's own query (`MediaListQuery`: `ORDER BY takenAt DESC, id DESC`), opened at the tapped tile's ordinal (`ViewerStart`), so its order always matches the grid; `FixStartPage` corrects the page if the list changed meanwhile.
- Zoom: Telephoto with Coil 3 sub-sampling (tiled decoding of big photos), up to 4× beyond 1:1. Double-tap cycles Fit → Fill → 1:1 around the tapped point (`nextDoubleTapZoom`), in increasing zoom, skipping levels below the display mode's own zoom. Two-finger rotation is view only and settles on quarter turns.
- Telephoto sizes: `transformation.scale` and `zoomTo()` are relative to the photo's own pixels. Get that size with `unscaledContentSize()` (fitted bounds over the initial scale); converting `unscaledContentBounds` into `ZoomableContent` coordinates divides by the current zoom instead.
- Display modes map to `ContentScale` (Stretch = `FillBounds`). The mode, zoom lock and slideshow options live in `ViewerSession` for the app's lifetime; Settings (Phase 6) persists them.
- Formats come from the file's own bytes (`ImageTraitsReader`): the XMP in the first 256 KB (Google Motion Photo container, older `GCamera:MicroVideo`, `GPano` photo spheres), Samsung's `SEFH`/`SEFT` trailer (`MotionPhoto_Data`), and Ultra HDR as `Bitmap.hasGainmap()` on a 1/32 decode (API 34+). A motion photo's video plays in place through a data source over the file at its offset; nothing is copied out.
- GIF and animated WebP play through coil-gif's `AnimatedImageDecoder`. Photo spheres render with one GLES2 fragment shader (equirectangular lookup per pixel, no sphere mesh), decoded at most 4096 px wide. Ultra HDR turns the window's colour mode to HDR while shown.
- Player: ExoPlayer lives in `PlayerViewModel` (keeps playing through rotation and picture-in-picture), a `MediaSession` takes media buttons, PiP auto-enters from Android 12. Subtitles are `.srt`/`.vtt` files with the video's name in its folder, found through MediaStore's subtitle type.
- Resume: Room v2 adds `playback_position` (cascade-deleted with its media row; auto-migration 1→2 with `MigrationTest`). Saved on pause, every few seconds and on leaving, through the app scope; a video resumes unless it was under 3 s in, within its last 3 s or past 95% (`resumePosition`).
- Details sheet: EXIF through ExifInterface; GPS needs `ACCESS_MEDIA_LOCATION`, asked from the sheet, and MediaStore's original-file URI. The mini map is Maps Compose lite mode and needs a Maps API key (README); without one the sheet shows the coordinates and Open in Maps. The Maps library adds the INTERNET permission; Phase 2 itself makes no network calls.
- detekt `ReturnCount` ignores guard clauses (`?: return null` is how the parsers read).
- Google Cloud project **PhotoXT** (id `photoxt`, Robin's account): Drive API on; Google Auth Platform External, in Testing, test users robinmorajker@gmail.com and robinmorajker2@gmail.com; scopes declared: openid, email, profile, drive.file, drive.appdata, drive, drive.readonly. Clients: Android for `com.photoxt.app` with the laptop debug key's SHA-1 (a release key needs its own), and a Web client whose id is Credential Manager's `serverClientId`.
- The Web client id comes from the Gradle property or environment variable `PHOTOXT_GOOGLE_WEB_CLIENT_ID` (laptop: `%USERPROFILE%\.gradle\gradle.properties`), never git. Without it the app builds and "Add Google account" says sign-in isn't set up.
- Modules added in Phase 3: `core/auth` (Credential Manager sign-in, `DriveAuth` on AuthorizationClient), `core/drive` (Drive v3 on Retrofit 3 + kotlinx-serialization, one OkHttp 5 client), `core/sync` (`DriveScanner`, `DriveSync`, `DeviceConditions`). Libraries, all §5.1: play-services-auth 22, credentials 1.6 + googleid 1.2, OkHttp, Retrofit, Media3 datasource-okhttp and database; mockwebserver3 for tests.
- Accounts: Credential Manager's `GetSignInWithGoogleOption` signs in (account id = the credential's `uniqueId`, else the ID token's `sub`); Drive access is asked per account through AuthorizationClient with `setAccount`. Play services keeps grants; `DriveAuth` holds an access token in memory only, 45 minutes per account. Requests carry the account as an OkHttp tag or the stripped `X-PhotoXT-Account` header; a 401 clears the token and retries once. A grant that needs the screen again flags the account (`needsConsent`) and Albums shows Reconnect.
- Room v3 (auto-migration 2→3): `account`, `tracked_folder`, `drive_folder`, plus Drive columns on `album` (accountId, parentId, rootId) and `media` (accountId, remoteId, remoteParentId, remoteVersion, md5, thumbnailLink, lat, lng, camera). Thumbnail and cache state live in side tables (`drive_thumbnail`, `drive_cache`), so writing them doesn't invalidate the paged media queries.
- Drive ids: albums `drive:<account>:<folderId>`, media `drive:<account>:<fileId>`. Nested mode makes an album per subfolder (`parentId`, all sharing the tracked folder's `rootId`); merge mode files everything into the root album. Albums lists only top-level albums, counting the whole tree; a Drive album shows its subfolders as a row of child albums.
- Scan (`DriveScanner`): changes start token saved first (so Phase 4's feed misses nothing), then a breadth-first `files.list` (1,000 a page, all drives, shortcuts resolved), one Room transaction per page, and a sweep of what's gone. State SCANNING → READY; an interrupted scan resumes at app start.
- Drive thumbnails: Drive's `thumbnailLink` at `=s512` (refreshed once through `files.get` when it answers 401/403/404/410), else the JPEG's EXIF thumbnail from its first 128 KB, a video frame over the authorised stream, or the whole image up to 30 MB. Saved as WebP (384 px short edge) at `thumbs/grid/ab/cd/<fileId>_<version>.webp`, with a 4×3 BlurHash in `drive_thumbnail`. A priority queue (visible, album, background; 6 downloads) fills them; background filling pauses on metered networks and in power saving.
- Drive originals: downloaded to `media/<account>/<fileId>_<version>.<ext>` through a `.part` file resumed with Range, checked against size and MD5, then a 1,600 px preview WebP. The viewer shows the BlurHash and progress until the file is there (Telephoto needs a file to tile).
- Drive video: Media3 `CacheDataSource` over `OkHttpDataSource` (the authorised client), `SimpleCache` in `cacheDir/exo` (1 GB LRU), cache key `drive:<fileId>@<version>`.
- `MediaSource` (core/media) is the source abstraction: `DeviceSource` and `DriveSource` give thumbnails and streams from an offset, with `canWrite`/`canShare`. The old `MediaSource` enum is now `SourceType` (DEVICE, DRIVE).
- Phase 3 spike findings (A15, 2026-11-05/06): the upgrade from `drive.readonly` to `drive` is incremental, and tokens afterwards carry every granted scope. In Testing each new consent shows "Google hasn't verified this app" first, and the consent page's Continue needs a scroll. After `revokeAccess` the next request needs the screen, the account is flagged and Reconnect asks for `drive.readonly` only; the 7-day Testing expiry takes the same path (not waited for).
- `thumbnailLink` (spike): comes as `=s220`; `=sN` gives a JPEG at that long edge, `-rw` a WebP at about half the bytes, `wN-hN` fits a box and `-c` crops. A fresh link works with or without the Authorization header; 18 hours later it answers 403 (HTML). A `files.get` with only some fields must still ask for `id` (DriveFile needs it).
- Changes API (spike): a file another account added to a folder shared with the user reached the user's feed within 10 s, in both the plain and the all-drives feed, so one feed per account covers shared-with-me. Shared drives aren't testable on personal accounts; Google's docs say the user feed with `includeItemsFromAllDrives` and `supportsAllDrives` (no `driveId`) includes the shared drives the user belongs to, so Phase 4 can keep one token per account.
- Range streaming (spike and Done when): ExoPlayer read the 1 GB test video's `moov` from its end with a Range request, and a seek to 7:10 resumed downloading at byte 751 MB.
- Sorting was added to both specs on 2026-11-06 (§4.2, built in Phase 6): the Albums tab, item lists and the Pictures timeline, each in both directions. Camera and Screenshots become automatic pins; in Phase 6 that replaces the fixed Camera-then-Screenshots order in `AlbumsViewModel`'s `arrange`.
- The spec's `album.customOrder` (never built) is now `album.position`, an album's place in Custom order; item drag order goes in a new `item_order` table.
- Date added isn't stored yet: the MediaStore indexer reads `DATE_ADDED` and the Drive scanner fetches `createdTime` (folders too), but only as takenAt fallbacks. Phase 6 adds `media.addedAt` and `album.createdAt` and must fill existing rows (migration plus rescan).
- Modules added in Phase 4: `core/datastore` (the spec's §5.2 settings module: a typed DataStore of `PxtSettings` stored as JSON through kotlinx.serialization, so no protobuf plugin) and `feature/library` (the Library tab and the Storage screen). Libraries, all §5.1: DataStore 1.3, WorkManager 2.12.
- Settings: `SettingsStore` holds `PxtSettings`; Phase 4 has `storage` (retention days, cache and preview caps, prefetch, mobile originals). Unknown keys are skipped, missing ones take defaults, a damaged file falls back to defaults. Later phases add their groups to `PxtSettings`.
- Room v4 (auto-migration 3→4; `Version3To4` drops `drive_cache.offlinePinned`): `offline_pin` (one row per pinned item, cascade-deleted with it; the Offline filter reads it), `drive_orphan` (files of Drive items that left: account, fileId, version, MD5, size, cache path, pin, `purgeAfter`) and `tracked_folder.offline`.
- Content version: Drive raises `version` on every change, renames and stars included, so an item keeps its stored `remoteVersion` (which keys its thumbnail, preview and cached files) while MD5 and size stay the same (`DriveItems.sameContent`; without an MD5, by version). New content orphans the old version's files, due at once, so the thumbnail is made again.
- Changes feed (`DriveChanges`): one token per account (user feed, all drives); each page is applied in one Room transaction with the next token. Known files are upserted into their parent folder's album; a renamed folder retitles its album and its tree's paths; a new folder, a folder moved, or an item whose parent isn't known marks the tree SCANNING for a rescan; a tracked root binned or gone (404) turns UNAVAILABLE and keeps its items; an expired token (400/404/410) takes a new start token and rescans every tree.
- Items removed in Drive become orphans for 7 days (`ORPHAN_GRACE_MS`): one back from the bin within that time takes its old version, cached original and pin back; then the daily cleanup deletes the files.
- Sync triggers: periodic unique work `drive-sync` every 6 h (network, battery not low), return to the foreground (30 s debounce), and pull-to-refresh in an album or Albums (waits, toast on failure). Scans, change syncs and removals of one account share a `Mutex` in `DriveSync`.
- WorkManager starts on demand: `PhotoXtApplication` is a `Configuration.Provider` and the manifest removes `WorkManagerInitializer`. Workers reach Hilt through `SyncEntryPoint` (no hilt-work dependency).
- Cache rules (`DriveCache.cleanUp`, daily `drive-cache-cleanup` and on a settings change): purge due orphans; evict originals not opened within the retention (30 days, `drive_cache.lastOpenedAt`) unless pinned; trim video spans by `lastTouchTimestamp`; then least recently opened originals over the cap (5 GB) and least recently used previews (file mtime, touched on use) over theirs (1 GB). Caps are decimal MB (`StorageSettings.MB`), as Android's `Formatter` shows sizes.
- Offline pins: pinned originals live in `media-offline/<account>/` (moved there if cached, else downloaded) by unique work `drive-offline-pins` (unmetered unless originals may use mobile data). "Make available offline" on a Drive album sets `tracked_folder.offline`, which pins its tree, later arrivals included.
- Data saver: on a metered network the viewer opens the 1,600 px preview (`thumbnailLink` at `=s1600`, kept as the preview WebP) with *Load original*, plus *Always* when set to Ask; default Wi-Fi only. Prefetch (2 each side) skips metered networks unless originals always load.
- Hidden tabs keep their ViewModels (see Navigation), so a screen showing state that Room doesn't observe re-reads it in `LifecycleStartEffect` (Storage measures its files each time it shows).
- detekt: TooManyFunctions ignores private functions and allows 15 per class; LongParameterList also skips `@GET`, `@Inject` and `@AssistedInject`.

## Known limits
- detekt 1.23.8, the latest stable, calls Gradle APIs that Gradle 10 removes. Move to detekt 2 once it is stable.
- At 200% text on a 360 dp phone, bottom-bar labels wrap mid-word (Material 3 default). Revisit in the accessibility pass.
- Screenshot goldens were recorded on Linux, as CI runs. If only screenshot tests fail on Windows with tiny text differences, trust CI or re-record on Linux.
- Robin's test phone is a Galaxy A15 5G (SM-A156E, One UI 8 / Android 16), reachable from robin-laptop over wireless adb. Its library holds about 23,800 photos and videos on two volumes (internal and SD card), enough for the 20,000-item checks.
- Grid scroll on the A15 (Phase 1, `ScrollBenchmark`: release build with Baseline Profile, 8 full-speed flings through 23,781 items, 5 runs): frame overrun P50 −0.2 / P90 5.8 / P95 9.6 / P99 22.1 ms with software thumbnails, against 1.6 / 9.4 / 14.2 / 33.9 ms with hardware bitmaps under the same conditions. About 2% of frames miss the app deadline (trace), short of the §5.8 budget of under 1% janky frames, which Phase 15 must meet. Most remaining misses are rows composing mid-fling and the GPU queue being full.
- Benchmarks on the A15: run them detached through WPSC (`am instrument -w -e class com.photoxt.baselineprofile.ScrollBenchmark com.photoxt.baselineprofile/androidx.test.runner.AndroidJUnitRunner`), about 6 minutes. Compare runs only under the same conditions; the phone runs warm after a profile generation.
- Driving the phone through WPSC: run anything long (installs over a slow link, instrumentation) detached, e.g. `Start-Process cmd.exe "/c adb ... > file 2>&1" -WindowStyle Hidden`, then read the file. A command that leaves a child holding the channel's output pipe (adb starting its server) hangs WPSC until that child exits; Cloudflare also cuts requests at 100 s.
- On the phone, `cp` into /sdcard does not reach MediaStore; save test photos with `content call --uri content://media --method scan_file --arg <path>` after copying, as an app would.
- The phone syncs the Projects folder to its SD card, so files under `build/cowork` (test images, screenshots) show up in its galleries; that folder has a `.nomedia` file. Better: exclude `build`, `.gradle` and `.kotlin` in the sync tool.
- Git from a Cowork session: its device shell can't delete files, so git there leaves `.lock` files. Run git on Windows instead, through WPSC (Git for Windows is installed): Phase 1 was committed in the cloud, copied over as a bundle into `build/cowork`, then `git fetch <bundle> main` and `git merge --ff-only FETCH_HEAD` on Windows.
- Debug signing: every Cowork cloud workspace makes its own `~/.android/debug.keystore`, and a build signed with another key can't install over the last one. Copy the laptop's `C:\Users\Robin Morajker\.android\debug.keystore` (Android Studio's) into the cloud's `~/.android/` before building, so updates keep the app's data. Phase 1's build had a throwaway key, so Phase 2 needed one uninstall (Robin agreed).
- Cloud → laptop file transfer: `device_commit_files` refuses staged paths over about 8 MB, and JPEGs sent that way arrive altered. Big binaries go intact through `SendUserFile` first and then `device_commit_files` with its `fileUuid` (52 MB APKs and the 1 GB test video, Phase 3). Otherwise gzip or split into `.part` files and check the SHA-256.
- Wireless adb: address the phone by its serial `adb-RZCX92ENX4J-X7P7RR._adb-tls-connect._tcp`; transport ids change with every reconnect. When the phone vanishes from `adb devices` and `adb mdns services`, Wireless debugging is off on the phone (it switches off when Wi-Fi drops) and only Robin can turn it back on.
- Robin's phone runs accessibility services (Tasker, AutoInput), so Compose keeps its accessibility semantics up to date on every frame. With that, debug builds run viewer transitions at about 150 ms a frame; judge smoothness only on `benchmarkRelease` with the Baseline Profile.
- Zoom on the A15 (Phase 2, `ZoomBenchmark`, 200 MP photo, `benchmarkRelease` with profile, Android Studio mirroring on): frame overrun P50 0.5 / P90 6.9 / P95 9.7 / P99 16.6 ms, on par with grid scrolling; 9–22% of frames miss the app deadline, mostly while 2,040 × 1,530 tiles upload on the render thread (10–18 ms each). Hardware-bitmap tiles measured no better. Phase 15's performance pass.
- Telephoto 0.19 leaks a file descriptor in `UriImageSource` (StrictMode `LeakedClosableViolation` on every big photo); library code, report upstream.
- Macrobenchmark: `StartupMode.COLD` kills the app after the setup block, under the measured interaction; interaction benchmarks call `killProcess()` at the start of setup and pass no startup mode. Android Studio's device mirroring makes Macrobenchmark refuse to run: stop mirroring, or pass `-e androidx.benchmark.suppressErrors DEVICE-MIRRORING`.
- Baseline Profile: regenerate it on the phone (install `app-nonMinifiedRelease` and `baselineprofile-nonMinifiedRelease`, run `BaselineProfileGenerator` with `am instrument`, pull `BaselineProfileGenerator_generate-baseline-prof.txt` from `/sdcard/Android/media/com.photoxt.baselineprofile/`) and copy it to `app/src/main/baseline-prof.txt`.
- Phone scripting through `adb shell`: `input tap x y; sleep 0.09; input tap x y` is a double tap; `uiautomator dump` fails while a video plays; One UI grants `ACCESS_MEDIA_LOCATION` without a dialog once photo access is granted.
- `PxtLog` masks `code=…` (meant for OAuth codes), so log HTTP statuses as "HTTP 403". Over WPSC, PowerShell mangles nested quotes for `adb shell`: push a script to `/data/local/tmp` and run it (with `run-as com.photoxt.app` for app files).
- The Cowork device shell writes to the connected folder at about 0.2 MB/s and its background processes die with each call: make big test files in the cloud and send them as above.
- Drive test data for Phase 3 (2,000 generated photos and a 1 GB video with its time burnt in) was uploaded with Drive for desktop into `G:\My Drive\PhotoXT test` and deleted after the checks.
- Drive test data for Phase 4: the folder "PhotoXT sync test" (10 generated photos) in My Drive, changed on drive.google.com in Robin's Chrome; binned after the checks (its last check: the binned folder turned the album unavailable).
- Removing a Drive album or account deletes its thumbnails, previews, downloaded and offline originals, and its videos' cached spans (by cache key).
- Phase 4 gaps: a Drive shortcut deleted for good stays until its tree is rescanned (the change names no parent); Slideshow and Compare load originals regardless of data saver; an album's status shows "Syncing" only for scans; nested albums of an unavailable tree show no banner, only its top album.
- Debug StrictMode still reports, none of it PhotoXT's own disk or network use: a library's main-thread SharedPreferences cleanup, One UI's `FactoryTest`/`IdsController` and `Toast.show` (a file check in `PackageManager.isSpeg`, so every toast reports with the caller's frame), and one untagged OkHttp socket (tag sockets through a SocketFactory if traffic attribution is ever needed).

## Where things live
- Specs: [photoxt-build-prompt.md](photoxt-build-prompt.md) (PhotoXT) and [photoxtpro-build-prompt.md](photoxtpro-build-prompt.md) (PhotoXTPro) are the source of truth. Copies sit in the Claude project knowledge under `claude/` with the same names; re-upload them after editing the folder copies.
- Code: `app/` (shell, navigation, tabs, overlays, Coil image loader), `core/model`, `core/common` (PxtLog), `core/database` (Room, timeline and viewer queries, playback positions, Drive tables), `core/auth`, `core/drive`, `core/sync` (scanner, Changes feed, `DriveItems`, offline pins, WorkManager jobs, `DriveSync`), `core/datastore` (settings), `core/media` (indexer, `DeviceMediaSync`, access, thumbnail fetcher, image traits, EXIF details, subtitles, share, media sources, Drive thumbnails, originals, video and `DriveCache`), `core/designsystem` (theme, header, icons), `core/ui` (media grid, fast scroller, access views, EmptyState, hero flight, window effects), `feature/timeline`, `feature/albums`, `feature/viewer`, `feature/player`, `feature/library` (Library, Storage), `baselineprofile/` (profile generator, startup and scroll benchmarks), `build-logic/` (convention plugins).
- Maps API key for the details sheet's mini map: Gradle property or environment variable `PHOTOXT_MAPS_API_KEY` (e.g. in `~/.gradle/gradle.properties`), never in git. See README.
