# Memory — PhotosXT

Durable facts and decisions that a future session would otherwise have to rediscover. One line each; delete a line when it stops being true. Status and in-progress work belong in `.session/` logs, not here.

## Decisions
- App name is **PhotoXT**; the folder and the Claude project are named PhotosXT.
- Stack: native Android, Kotlin + Jetpack Compose (chosen over Kotlin Multiplatform and Flutter, 2026-11-04).
- Audience: private first (family, up to 100 Google accounts), kept Play Store-ready for a later public launch (2026-11-04).
- SDK levels: minSdk 30 (Android 11), targetSdk and compileSdk 37 (Android 17). Google Play requires target 36+ since 31 Aug 2026.
- Backend: Firebase in asia-south1 (Auth, Firestore, Functions, Hosting, Storage, FCM, App Check). It is used only for public albums, boards, share-link records and invites.
- Drive scopes: `drive.readonly` when the first folder is added, upgrade to `drive` on the first write, `drive.appdata` for settings sync. `drive.file` + Google Picker can't list a picked folder's contents: re-tested in the Phase 3 spike (2026-11-06), the picked folder itself is readable but 0 of its 2,001 children are listed.
- Data boundary: Drive content, Drive metadata and OAuth tokens never leave the device. Why: restricted-scope data stored on or sent to servers triggers Google's yearly security assessment.
- Sharing with people uses Drive permissions; the Shared Albums "With me" view reads Drive `sharedWithMe`. Links are Android App Links on the Firebase Hosting domain (Firebase Dynamic Links shut down in Aug 2025).
- Google Cloud for private use: in Testing status, grants expire every 7 days. In production but unverified, users see a warning and the project is capped at 100 users.
- Two editions (2026-11-04): PhotoXTPro is the full spec, including public media boards. PhotoXT is the same spec without media boards; Public Albums stay, since only boards were asked to go. Section and phase numbers match in both specs.
- One codebase for both editions (Robin, 2026-11-04). Build PhotoXT now; add the `pro` product flavor (PhotoXTPro) in this repo when board work starts (Phase 12). No flavors before that.
- Git and CI (Robin, 2026-11-04): this folder is the repo root, branch `main`. The remote `origin` is github.com/RobinMorajker/PhotosXT (Phase 0 pushed by Robin). CI is `.github/workflows/ci.yml` and runs on every push to `main`; the same command runs locally (see README "Build and check"). Sessions commit locally; Robin pushes.
- Toolchain (pinned 2026-11-04 in `gradle/libs.versions.toml`): Gradle 9.8.2, AGP 9.5.0 with built-in Kotlin (never apply `org.jetbrains.kotlin.android`), Kotlin 2.4.21, KSP 2.3.13, Hilt 2.60.1, Compose BOM 2026.09.00 (Material 3 1.4.0), Navigation 3 1.2.0. Builds need JDK 17+; CI uses 21.
- `applicationId` and namespace are the placeholder `com.photoxt.app` until open decision 1 (spec §9) is settled, before Phase 11.
- Navigation: one Navigation 3 back stack per tab, each with its own saveable-state and ViewModel-store decorators, so a tab keeps its state and ViewModels while hidden (nav3-recipes "multiple back stacks"). Back exits through Pictures. An album opens as `AlbumKey` on the Albums stack.
- One UI header: `PxtCollapsingHeader` in core/designsystem on Material 3's exit-until-collapsed scroll behaviour. Expanded = 40% of the window height, collapsed = 64 dp, and no expansion on windows under 480 dp tall. A bottom toolbar row holds the navigation icon, actions and the collapsed title; every header carries the test tag `PXT_HEADER_TEST_TAG`.
- Logging: only `PxtLog` (core/common). It redacts tokens, e-mails, URIs, paths, media file names and coordinates; debug StrictMode reports through it.
- No Android cloud backup or device-to-device transfer (`allowBackup`/`fullBackupContent` false, `data_extraction_rules.xml` excludes everything). Settings restore through the user's Drive app-data folder (spec §4.8) instead.
- Theme: dynamic colour by default; without it, the Material 3 baseline scheme until the accent setting exists (§4.20). AMOLED black is `PxtTheme(amoledBlack = true)` and gets a user setting with the other theme options.
- Icons: Material Symbols Rounded, as vector drawables in core/designsystem (`ic_tab_*`). Not `material-icons-extended`.
- `baselineprofile/` holds both the Baseline Profile generator and the Macrobenchmark startup test (Android Studio's layout); there is no separate `benchmark/` module.
- Quality gates run from the root: Spotless with ktlint `android_studio` style (100 columns, no trailing commas), detekt 1.23.8, and Android Lint with warnings as errors (version-age checks and `ObsoleteLintCustomCheck` disabled).
- Modules added in Phase 1: `core/model` (plain Kotlin types; uses the Android library convention, no Android APIs), `core/database` (Room), `core/media` (MediaStore indexer, access, thumbnails), `feature/timeline` (Pictures and the grid of one album) and `feature/albums`. Hilt modules use the `photoxt.android.hilt` convention plugin.
- Room v1 (Phase 1): `album`, `media` and `media_store_cursor` (per volume: MediaStore version, generation and the time zone of the day keys). Schemas are exported to `core/database/schemas`; every later version needs a migration test.
- Ids: device media `device:<MediaStore _ID>`, device albums `device:<BUCKET_ID>`. `media.dayKey` and `monthKey` are local-calendar keys of `takenAt` (epoch day; year*12+month-1), so SQL can group; a time-zone change rescans.
- Timeline rows come from one UNION query (each date header, then its items) paged by Room with placeholders and jumps, so headers sit at exact positions. `TimelineLayout` (core/ui) is built from the same query's group counts: placeholder spans, fast-scroller labels, select-all counts, and keeping the same photo in view when the grouping changes.
- Pinch density, densest first: year (12 columns), month (9), then days at 7 down to 1 columns; default 4. Wider windows multiply the columns per 360 dp. The last density persists in `PxtSettings.view`, one for Pictures and one for every album (Phase 6).
- MediaStore indexer: per volume, a generation scan of changed items. An id diff (deletions, plus a direct fetch of ids Room has never seen) runs on every return to the foreground, after permission answers and on MediaStore delete notifications; insert and edit notifications skip it. Full rescans only on a new MediaStore version or time zone. A failed query throws instead of looking like "nothing there".
- Device thumbnails: MediaStore's own thumbnail (`openTypedAssetFile` with `EXTRA_SIZE`), decoded by Coil at tile size into software bitmaps; at most 4 provider reads at a time. Nothing is written to PhotoXT's storage. Hardware bitmaps are off in the app's image loader because they made grid scrolling worse on the A15 (see Known limits); a full-size viewer image may opt back in per request.
- Grid gestures live on the grid, not the tiles: tap, long-press, drag-select with edge auto-scroll, and pinch. Tiles only declare semantics (TalkBack open, select, toggle). While selecting, the navigation bar hides and the selection action bar takes its place.
- Selection is a map of id to capture time in the ViewModel (not saved across process death). Share hands up to 500 items to the system share sheet.
- Permissions: READ_EXTERNAL_STORAGE up to API 32, READ_MEDIA_IMAGES/VIDEO from 33, plus READ_MEDIA_VISUAL_USER_SELECTED from 34. Limited access shows a banner with Manage (picker) and Allow all (app settings), because on One UI 8 asking again only offers the picker.
- detekt: LongParameterList ignores composables, MagicNumber ignores enums. Lint wants `toUri()`, so core-ktx is an explicit dependency.
- Tests: Robolectric runs Android 17, which needs `--add-opens java.base/jdk.internal.access` (set in build-logic) and espresso-core 3.7+ (pinned in app). Screenshot goldens live in `app/src/test/screenshots`; re-record with `./gradlew recordRoborazziDebug`. Screenshot tests click with semantics actions, because touch ripples differ between runs.
- Modules added in Phase 2: `feature/viewer` (pager, compare, slideshow, 360° view, details sheet) and `feature/player` (Media3). Libraries, all §5.1: Telephoto 0.19 (zoomable-image-coil3), Media3 1.11 (exoplayer, session, ui-compose), ExifInterface, coil-gif, Maps Compose 9, room-testing.
- Full-screen destinations (viewer, player, compare, slideshow, 360°) sit on one overlay back stack above the tabs (`app/Overlays.kt`), so the grid stays drawn under the viewer while it is swiped down. A covered overlay is not drawn and is hidden from TalkBack but keeps its state.
- Grid ↔ viewer transition: a hand-made flight (`MediaHero`, `HeroTiles` in core/ui) from the tapped tile's bounds, not `SharedTransitionLayout`, which would put the whole app and every grid scroll inside a lookahead scope. The tile hides while its photo flies; on close the grid scrolls the current item into view first. After process death the viewer fades in instead.
- The viewer pages the grid's own query (`MediaListQuery`, with the grid's sort and Library list in `ViewerStart`), opened at the tapped tile's ordinal, so its order always matches the grid; `FixStartPage` corrects the page if the list changed meanwhile, which also lets History and Bookmarks open an item at index 0 of its own album.
- Zoom: Telephoto with Coil 3 sub-sampling (tiled decoding of big photos), up to 4× beyond 1:1. Double-tap cycles Fit → Fill → 1:1 around the tapped point (`nextDoubleTapZoom`), in increasing zoom, skipping levels below the display mode's own zoom. Two-finger rotation is view only and settles on quarter turns.
- Telephoto sizes: `transformation.scale` and `zoomTo()` are relative to the photo's own pixels. Get that size with `unscaledContentSize()` (fitted bounds over the initial scale); converting `unscaledContentBounds` into `ZoomableContent` coordinates divides by the current zoom instead.
- Display modes map to `ContentScale` (Stretch = `FillBounds`). The mode, zoom lock and slideshow options live in `ViewerSession`, loaded from and saved to `PxtSettings.view` (Phase 6), so they sync with the settings.
- Formats come from the file's own bytes (`ImageTraitsReader`): the XMP in the first 256 KB (Google Motion Photo container, older `GCamera:MicroVideo`, `GPano` photo spheres), Samsung's `SEFH`/`SEFT` trailer (`MotionPhoto_Data`), and Ultra HDR as `Bitmap.hasGainmap()` on a 1/32 decode (API 34+). A motion photo's video plays in place through a data source over the file at its offset; nothing is copied out.
- GIF and animated WebP play through coil-gif's `AnimatedImageDecoder`. Photo spheres render with one GLES2 fragment shader (equirectangular lookup per pixel, no sphere mesh), decoded at most 4096 px wide. Ultra HDR turns the window's colour mode to HDR while shown.
- Player: ExoPlayer lives in `PlayerViewModel` (keeps playing through rotation and picture-in-picture), a `MediaSession` takes media buttons, PiP auto-enters from Android 12. Subtitles are `.srt`/`.vtt` files with the video's name in its folder, found through MediaStore's subtitle type.
- Resume: Room v2 adds `playback_position` (auto-migration 1→2 with `MigrationTest`); since v6 it has no foreign key, so settings sync can restore it before its item is indexed again, and *Continue watching* joins `media` so a gone item never shows. Saved on pause, every few seconds and on leaving, through the app scope; a video resumes unless it was under 3 s in, within its last 3 s or past 95% (`resumePosition`).
- Details sheet: EXIF through ExifInterface; GPS needs `ACCESS_MEDIA_LOCATION`, asked from the sheet, and MediaStore's original-file URI. The mini map is Maps Compose lite mode and needs a Maps API key (README); without one the sheet shows the coordinates and Open in Maps. The Maps library adds the INTERNET permission; Phase 2 itself makes no network calls.
- detekt `ReturnCount` ignores guard clauses (`?: return null` is how the parsers read).
- Google Cloud project **PhotoXT** (id `photoxt`, Robin's account): Drive API on; Google Auth Platform External, in Testing, test users robinmorajker@gmail.com and robinmorajker2@gmail.com; scopes declared: openid, email, profile, drive.file, drive.appdata, drive, drive.readonly. Clients: Android for `com.photoxt.app` with the laptop debug key's SHA-1 (a release key needs its own), and a Web client whose id is Credential Manager's `serverClientId`.
- The Web client id comes from the Gradle property or environment variable `PHOTOXT_GOOGLE_WEB_CLIENT_ID` (laptop: `%USERPROFILE%\.gradle\gradle.properties`), never git. Without it the app builds and "Add Google account" says sign-in isn't set up.
- Modules added in Phase 3: `core/auth` (Credential Manager sign-in, `DriveAuth` on AuthorizationClient), `core/drive` (Drive v3 on Retrofit 3 + kotlinx-serialization, one OkHttp 5 client), `core/sync` (`DriveScanner`, `DriveSync`, `DeviceConditions`). Libraries, all §5.1: play-services-auth 22, credentials 1.6 + googleid 1.2, OkHttp, Retrofit, Media3 datasource-okhttp and database; mockwebserver3 for tests.
- Accounts: Credential Manager's `GetSignInWithGoogleOption` signs in (account id = the credential's `uniqueId`, else the ID token's `sub`); Drive access is asked per account through AuthorizationClient with `setAccount`. Play services keeps grants; `DriveAuth` holds an access token in memory only, 45 minutes per account. Requests carry the account as an OkHttp tag or the stripped `X-PhotoXT-Account` header; a 401 clears the token and retries once. A grant that needs the screen again flags the account (`needsConsent`) and Albums shows Reconnect.
- Room v3 (auto-migration 2→3): `account`, `tracked_folder`, `drive_folder`, plus Drive columns on `album` (accountId, parentId, rootId) and `media` (accountId, remoteId, remoteParentId, remoteVersion, md5, thumbnailLink, lat, lng, camera). Thumbnail and cache state live in side tables (`drive_thumbnail`, `drive_cache`), so writing them doesn't invalidate the paged media queries.
- Drive ids: albums `drive:<account>:<folderId>`, media `drive:<account>:<fileId>`. Nested mode makes an album per subfolder (`parentId`, all sharing the tracked folder's `rootId`); merge mode files everything into the root album. Albums lists only top-level albums, counting the whole tree; a Drive album shows its subfolders as a row of child albums.
- Scan (`DriveScanner`): changes start token saved first (so Phase 4's feed misses nothing), then a breadth-first `files.list` (1,000 a page, all drives, shortcuts resolved), one Room transaction per page, and a sweep of what's gone. State SCANNING → READY; an interrupted scan resumes at app start.
- Drive thumbnails: Drive's `thumbnailLink` at `=s512` (refreshed once through `files.get` when it answers 401/403/404/410), else the JPEG's EXIF thumbnail from its first 128 KB, a video frame over the authorised stream, or the whole image up to 30 MB. Saved as WebP (384 px short edge) at `thumbs/grid/ab/cd/<fileId>_<version>.webp`, with a 4×3 BlurHash in `drive_thumbnail`. A priority queue (visible, album, background; 6 downloads) fills them; background filling pauses on metered networks and in power saving.
- Drive originals: downloaded to `media/<account>/<fileId>_<version>.<ext>` through a `.part` file resumed with Range, checked against size and MD5, then a 1,600 px preview WebP. The viewer shows the BlurHash and progress until the file is there (Telephoto needs a file to tile).
- Drive video: Media3 `CacheDataSource` over `OkHttpDataSource` (the authorised client), `SimpleCache` in `cacheDir/exo` (1 GB LRU), cache key `drive:<fileId>@<version>`.
- `MediaSource` (core/media) is the source abstraction: `DeviceSource` and `DriveSource` give thumbnails and streams from an offset, with `canWrite`/`canShare`. The old `MediaSource` enum is now `SourceType` (DEVICE, DRIVE).
- Phase 3 spike findings (A15, 2026-11-05/06): the upgrade from `drive.readonly` to `drive` is incremental, and tokens afterwards carry every granted scope. In Testing each new consent shows "Google hasn't verified this app" first, and the consent page's Continue needs a scroll. After `revokeAccess` the next request needs the screen, the account is flagged and Reconnect asks for `drive.readonly` only; the 7-day Testing expiry takes the same path (not waited for).
- `thumbnailLink` (spike): comes as `=s220`; `=sN` gives a JPEG at that long edge, `-rw` a WebP at about half the bytes, `wN-hN` fits a box and `-c` crops. A fresh link works with or without the Authorization header; 18 hours later it answers 403 (HTML). A `files.get` with only some fields must still ask for `id` (DriveFile needs it).
- Changes API (spike): a file another account added to a folder shared with the user reached the user's feed within 10 s, in both the plain and the all-drives feed, so one feed per account covers shared-with-me. Shared drives aren't testable on personal accounts; Google's docs say the user feed with `includeItemsFromAllDrives` and `supportsAllDrives` (no `driveId`) includes the shared drives the user belongs to, so Phase 4 can keep one token per account.
- Range streaming (spike and Done when): ExoPlayer read the 1 GB test video's `moov` from its end with a Range request, and a seek to 7:10 resumed downloading at byte 751 MB.
- Sorting was added to both specs on 2026-11-06 (§4.2) and built in Phase 6: the Albums tab, item lists and the Pictures timeline, each in both directions. Camera and Screenshots are pinned automatically the first time they are seen (`OrganizeSettings.autoPinned`, so an unpin sticks).
- An album's place in the Albums tab's Custom order is `album_prefs.position` (the spec's `album.customOrder`); item drag order is the `item_order` table.
- Modules added in Phase 4: `core/datastore` (the spec's §5.2 settings module: a typed DataStore of `PxtSettings` stored as JSON through kotlinx.serialization, so no protobuf plugin) and `feature/library` (the Library tab and the Storage screen). Libraries, all §5.1: DataStore 1.3, WorkManager 2.12.
- Settings: `SettingsStore` holds `PxtSettings`; Phase 4 has `storage` (retention days, cache and preview caps, prefetch, mobile originals). Unknown keys are skipped, missing ones take defaults, a damaged file falls back to defaults. Later phases add their groups to `PxtSettings`.
- Room v4 (auto-migration 3→4; `Version3To4` drops `drive_cache.offlinePinned`): `offline_pin` (one row per pinned item, cascade-deleted with it; the Offline filter reads it), `drive_orphan` (files of Drive items that left: account, fileId, version, MD5, size, cache path, pin, `purgeAfter`) and `tracked_folder.offline`.
- Content version: Drive raises `version` on every change, renames and stars included, so an item keeps its stored `remoteVersion` (which keys its thumbnail, preview and cached files) while MD5 and size stay the same (`DriveItems.sameContent`; without an MD5, by version). New content orphans the old version's files, due at once, so the thumbnail is made again.
- Changes feed (`DriveChanges`): one token per account (user feed, all drives); each page is applied in one Room transaction with the next token. Known files are upserted into their parent folder's album; a renamed folder retitles its album and its tree's paths; a new folder, a folder moved, or an item whose parent isn't known marks the tree SCANNING for a rescan; a tracked root binned or gone (404) turns UNAVAILABLE and keeps its items; an expired token (400/404/410) takes a new start token and rescans every tree.
- Items removed in Drive become orphans for 7 days (`ORPHAN_GRACE_MS`): one back from the bin within that time takes its old version, cached original and pin back; then the daily cleanup deletes the files.
- Sync triggers: periodic unique work `drive-sync` every 6 h by default (Settings offers 1–24 h, on any network or Wi-Fi only; `SyncWork.schedule` re-enqueues with `UPDATE` when they change), return to the foreground (30 s debounce), and pull-to-refresh in an album or Albums (waits, toast on failure). Scans, change syncs and removals of one account share a `Mutex` in `DriveSync`.
- WorkManager starts on demand: `PhotoXtApplication` is a `Configuration.Provider` and the manifest removes `WorkManagerInitializer`. Workers reach Hilt through `SyncEntryPoint` (no hilt-work dependency).
- Cache rules (`DriveCache.cleanUp`, daily `drive-cache-cleanup` and on a settings change): purge due orphans; evict originals not opened within the retention (30 days, `drive_cache.lastOpenedAt`) unless pinned; trim video spans by `lastTouchTimestamp`; then least recently opened originals over the cap (5 GB) and least recently used previews (file mtime, touched on use) over theirs (1 GB). Caps are decimal MB (`StorageSettings.MB`), as Android's `Formatter` shows sizes.
- Offline pins: pinned originals live in `media-offline/<account>/` (moved there if cached, else downloaded) by unique work `drive-offline-pins` (unmetered unless originals may use mobile data). "Make available offline" on a Drive album sets `tracked_folder.offline`, which pins its tree, later arrivals included.
- Data saver: on a metered network the viewer opens the 1,600 px preview (`thumbnailLink` at `=s1600`, kept as the preview WebP) with *Load original*, plus *Always* when set to Ask; default Wi-Fi only. Prefetch (2 each side) skips metered networks unless originals always load.
- Hidden tabs keep their ViewModels (see Navigation), so a screen showing state that Room doesn't observe re-reads it in `LifecycleStartEffect` (Storage measures its files each time it shows).
- detekt: TooManyFunctions ignores private functions, `@Dao` interfaces and the `@Database` class, and allows 14 per class and per interface (it flags 15); LongParameterList also skips `@GET`, `@POST`, `@PATCH`, `@DELETE`, Room's `@Query`, `@Inject` and `@AssistedInject`. A class that outgrows it is split by job (the engine, `Copier`, `TransferQueue`, `PastePlanner`), and a ViewModel hands its file operations to a plain helper (`TimelineFileOps`, `ViewerFileOps`).
- Module added in Phase 5: `core/transfer` (the clipboard, the transfer queue and engine, MediaStore writes in `DeviceStore`, Drive writes in `DriveFiles`, the unified Trash, batch tools, consents, the job that runs the queue). No new libraries; Drive writes extend `DriveApi`, and `DriveUploads` does resumable uploads.
- Room v5 (auto-migration 4→5): `transfer_batch` (one user action: op, title, conflict policy, paused, Undo links), `transfer_job` (source and destination as JSON `FileRef`/`Destination`, state, `waitFor`, attempts, next attempt, bytes, `JobProgress` JSON), `clipboard` (one row: cut or copy, media and album refs; it survives process death) and `album.pending`.
- Transfer engine: one job at a time, oldest batch first, from a drain under a mutex. Every copy is checked by size and MD5 (Drive's `md5Checksum`; a phone copy is read back) before anything else happens to it; a cut removes its source only after that (phone trash or Drive bin), and a copy that fails the check is deleted and retried. Retries back off 5 s doubling to 15 min, 6 attempts; no network requeues in 60 s without counting.
- Resuming: a job saves `JobProgress` about once a second. Drive copies, uploads and folders take ids from `files.generateIds` first, so a rerun finds the file instead of making a second; uploads keep the resumable session URL and ask Drive how much it holds; downloads go to `transfers/<jobId>.part` and resume with Range. Running jobs are requeued at the next drain.
- The queue runs as a user-initiated data transfer job when PhotoXT is on screen (Android 14+, `TransferJobService`, JobScheduler id 5005), else as WorkManager work in a `dataSync` foreground service. WorkManager's JobScheduler ids are 10,000–100,000 (`PhotoXtApplication`), clear of 5005; the periodic sync and cache jobs scheduled before that keep older ids, and all WorkManager jobs sit in JobScheduler namespace `androidx.work.systemjobscheduler`.
- When the queue starts in the background (a process start with work left), Android 16 refuses the worker's foreground service ("code:DENIED"); the work runs anyway and `TransferNotifications.showProgress` posts the progress as a plain notification under the same id (2026-11-10).
- Jobs that need the user wait (`WaitFor`): CONFLICT (Keep both / Replace / Skip, Apply to all), MediaStore's write, trash, restore and delete screens, the `drive` scope, and Drive files the user can't bin (take out of the album, or leave). The app asks while visible (`TransferPrompts`); while hidden, one "needs you" notification. Media management (`MANAGE_MEDIA`) skips MediaStore's screens. MediaStore's screen waits 1 s for the rest of a batch to reach the same wait, then asks once for all of it.
- Drive's Changes feed lists PhotoXT's own write up to several seconds late: after every write, `DriveSync.syncAfterWrite` syncs at once and again 5 s and 30 s later (a paste's last item stayed hidden until pull-to-refresh, 2026-11-10).
- Drive behaviours seen on the phone (2026-11-10): taking someone else's file out of a shared folder (`removeParents`) answers 204 with no body, since the caller can no longer see it (`DriveApi.removeParent` reads none), and the file goes to its owner's My Drive root; an editor's cut of the owner's file into the editor's own folder is a plain parents update that Drive allows, after which the owner no longer sees it in their folder; a rename sets `modifiedTime` to now, so PhotoXT sends the old one with every rename (videos and EXIF-less files are dated by it).
- Asking AuthorizationClient for `drive.readonly` when only `drive` was granted shows a consent screen; `DriveScope.toAsk` asks for `drive` whenever it is held (an account whose first act was *New album* got a second screen, and its background token would have flagged Reconnect).
- Matrix routes (`Copier`): Drive→Drive in one account copies with `files.copy` and moves with a parents update; phone→phone on one volume moves with `RELATIVE_PATH`; everything else copies through a pending MediaStore item or a resumable upload, and a cut then removes the source. Replace bins the item it replaces; Keep both adds " (1)". Undo queues the reverse batch (moves back, restores from trash, bins the copy of a cross-source cut).
- *New album* on the phone saves a pending album row with its final id (MediaStore's bucket id is the hash of the lower-cased folder path) until MediaStore shows the folder; in Drive it queues a folder job, and a folder at the top of My Drive becomes a tracked album. Empty albums lead the Albums list, after the Camera and Screenshots pins.
- A dialog that starts work after closing must launch it in its screen's scope: a scope remembered inside the dialog ends when it closes (the first *New album* never opened). A `LaunchedEffect` must not change its own key before a suspending call (the Drive consent prompt stuck).
- MediaStore: an item's own collection (images, video) has no `media_type` column, only the files collection does; read single items with `ITEM_PROJECTION`.

- Modules added in Phase 6: `core/organize` (pins, hiding, album options and groups, PhotoXT's own albums, bookmarks, history, settings sync) and `core/vault` (Tink streaming AEAD files and their Coil fetcher). Library, §5.1: Tink 1.24 (`tink-android`).
- Room v6 (auto-migration 5→6, `Version5To6`): `media.addedAt`, `addedDayKey/MonthKey`, `modifiedDayKey/MonthKey` and `nameKey`, with (albumId, key) indexes; `album.createdAt` and `rule`; tables `album_prefs` (cover, Custom-order position, group, hidden, hide from Pictures), `album_group`, `album_item` (virtual albums), `item_order`, `pin` (albums and items), `bookmark_collection`, `bookmark`, `history`, `hidden_item`. The migration clears `media_store_cursor` and sets READY trees SCANNING, so the phone and Drive are indexed again to fill the new columns.
- Name sort uses `nameKey` (`naturalKey`: lower case, each digit run as a zero-padded number, leading zeros dropped), so IMG_2 sorts before IMG_10 in SQL. Date added is MediaStore's `DATE_ADDED` and Drive's `createdTime`; an album's Date created is its own creation time, else its earliest Date added.
- Timeline SQL (`MediaSql`): one inner select gives each item a section (0 = pinned in this album, 1 = the rest), a group key (the sort's own day or month for date sorts, one group for Name, Size and Custom), a pin position and a sort key; rows, group counts, viewer items, ids and `ROW_NUMBER` positions all order by `section, groupKey, pinPos, sortKey, takenAt, id`. Pinned items sit under their own header in every sort; non-date sorts show no other headers. Custom order puts items without a place first, newest first. Only Custom order reads `item_order`, so the grids of the other sorts (`timelineRowsBySort`, `groupCountRowsBySort`) don't observe it.
- Sort scope (`SortSettings`): one sort for the Albums tab, one for Pictures, one per Library list, and each album its own (`perAlbum`, by album id), else `albumDefault`, which *Apply to all albums* sets after clearing every album's own. Album sorts live in the settings, not in Room: a write to `album_prefs` reloads every open grid, which made album sort switches twice as slow on the A15 (2026-11-15). A new sort clears the selection.
- Custom order (items and the Albums tab) starts from the order on screen the first time it is picked (items: one `INSERT OR IGNORE … SELECT` in id order, `seedCustomOrder`); after that it comes back as the user left it, new items and albums at the top. Claude's call on 2026-11-15, flagged to Robin: re-starting it at every pick replaced a dragged order with whichever sort was on screen. Deleting an own album clears its `item_order` rows.
- Albums tab order is computed in Kotlin (`arrange` in feature/albums): hidden albums out, grouped albums only inside their group (unless pinned), pins first in their drag order, then the sort; empty albums lead Newest item in both directions, new albums lead Custom order. Group tiles sort among the albums.

No snackbar for a favorite, only for its failure. MediaStore's IS_FAVORITE and Drive's `starred` flow back in through the indexer and the changes feed.

- Bookmarks keep the target's name at the time, a note, and for a video moment `positionMs` (the player's bookmark button; opening it starts there). A Drive item's grid thumbnail is copied to `filesDir/bookmarks/<id>.webp`, shown with "No longer available" once the item is gone.
- Hidden items count for nothing on album tiles (count, size, newest, cover, a chosen cover too), and bookmarks of hidden items and albums stay out of Bookmarks until unhidden (found on the A15, 2026-11-16).
- History logs a view per open (album context, watched time for videos through the player); *Recently viewed* groups by item. Incognito logs nothing, video positions included. Hidden items, items of hidden albums and vault items are never logged, and hiding or vaulting forgets what was. Auto-delete runs at each app start (default 12 months).
- Lock (`PrivateLock`, core/ui): Hidden, the vault, a hidden album and the Hidden list's viewer open after the platform `BiometricPrompt` with BIOMETRIC_STRONG or DEVICE_CREDENTIAL (no androidx.biometric). It locks again when the activity stops and whenever the Library tab's list shows, decided in the app shell (`Tabs`): NavDisplay can keep the list composed under the pages it opened, so the list's own effect didn't run again and Hidden stayed open (found on the A15, 2026-11-16). A screen restored behind the lock closes itself.
- Vault (Robin, 2026-11-12: the original is deleted for good once its encrypted copy reads back the same, on the phone and in Drive): Tink `AES256_GCM_HKDF_1MB` keyset in `noBackupFilesDir/vault-key`, encrypted by an Android Keystore key; files in `filesDir/vault` as `<id>.data/.thumb/.meta`, each bound to its id and part by associated data. Photos decrypt in memory through a Coil fetcher (thumbnails memory-cached only), videos through a seekable decrypting `VaultDataSource`; screens set FLAG_SECURE. Moving out writes the item back to its old folder (else Pictures/PhotoXT). The vault is this phone's only: uninstalling deletes it.
- Tink's keyset-level seekable channel knows its size only after a first read: `VaultDataSource` reads one byte before seeking (found by `VaultTest`).
- Settings sync (`SettingsSync`): one JSON `Snapshot` (settings without this phone's state, tracked Drive folders, own albums and their items, album options and groups, Custom order, pins, bookmarks, hidden items, history, resume points) as `photoxt-settings.json` in the backup account's `appDataFolder`, gzipped since 2026-11-16 (`Snapshots.pack`; `unpack` also reads the plain JSON the first builds wrote, by gzip's magic bytes) (first account added unless chosen). Changes upload 15 s after they settle through unique work `settings-sync` on any network, only when the snapshot's hash changed. A 24,000-item Custom order is 2.4 MB of JSON and about 145 KB gzipped (`SnapshotTest`), which is what each change uploads. Nothing uploads until this install has looked for a copy (`DeviceState.restoreChecked`); a reinstall restores when its first account signs in, then adds the restored Drive folders as their accounts sign in.
- Settings screen (Library → Settings): Storage, Drive sync interval and mobile data, history pause and auto-delete, settings sync on/off, account, status, *Allow* (the `drive.appdata` consent) and *Sync now*.

- Modules added in Phase 7: `core/render` (the recipe's geometry, one GLES 3.00 shader, preview session, tiled export, strip JPEG/PNG writers, EXIF copy, edit assets), `core/ml` (ML Kit detectors, LiteRT inpainting, eraser models) and `feature/editor`. Libraries, §5.1: ML Kit face 17.1.0, text 19.0.2 + Devanagari 16.0.2, subject segmentation 16.0.0-beta1; LiteRT through Play services (`play-services-tflite-java`/`-gpu` 16.5.0, so no interpreter in the APK); heifwriter 1.1.0 for HEIC and AVIF (Robin approved, 2026-11-16).
- Edit recipe (`EditRecipe`, core/model `Edit.kt`, JSON `EDIT_RECIPE_VERSION` 1): one value per tool, rendered in a fixed order whatever order the user worked in: erasures (patches baked into the source), geometry (EXIF orientation, quarter turns and flips, perspective, straighten cropped to fill, crop), redaction sampling, red-eye, skin, background blur, dehaze, white balance and exposure in linear light, tone, sharpen and clarity, curves, hue/HSL/saturation/vibrance, filter or LUT, local masks, fade/vignette/grain, solid redaction bars, cut-out background, frame; then drawings, text, stickers and the watermark are painted over each strip.
- Preview = export (spec §4.10): the preview and every export tile run the same shader, and everything it reads is a function of the source position: neighbourhood effects (clarity, dehaze, blurs, pixelate) read fixed 1,024 px guides of the whole photo, so a 2,048 px preview and a 50 MP export agree and tiles meet without seams.
- Export: 2,048 × 256 tiles, a strip at a time, straight into PhotoXT's own baseline JPEG and PNG writers, so a 200 MP photo never sits whole in memory. WebP, HEIC, AVIF and file-size targets need one whole bitmap (memory-checked; a size target searches for the best quality that fits, then shrinks the picture if even the lowest doesn't). *Save* keeps the photo's format, size and metadata at quality 95; GIF, RAW and other formats PhotoXT can't write offer *Save as copy* only.
- Edit assets (masks, erasure patches, LUTs, logos, stickers, background pictures) are content-addressed files in `filesDir/edits/assets` (SHA-256 names); recipes refer to them by name. At each app start `EditCleanup` keeps those named by an edit, a preset, a LUT, a sticker or the copied edit, plus anything under a day old.
- Save and Revert (Room v7, auto-migration 6→7, table `edit_recipe`): a phone photo's original is copied to `filesDir/edits/originals` and read back before it is first written over; a Drive photo's head revision is marked `keepForever` and the edit is uploaded as the file's next revision (resumable). Revert writes the kept bytes back; on Drive as a new revision checked against the original's MD5, after which the kept revision is deleted, because Drive never takes `keepForever` back (400 `illegalKeepForeverModification`, found on the phone 2026-11-18). Edits ride the transfer queue as EDIT, EDIT_COPY and REVERT, with resume, consent waits and Undo (a save's Undo restores the previous edit or the original). A phone save checks MediaStore write access (`DeviceStore.checkWrite`, `Context.checkUriPermission`) before it renders, so a pasted batch waits together for one consent screen. A photo gone from PhotoXT for 31 days loses its kept original.
- Unredacted reads: `MediaStoreDevice.open` reads through `MediaStore.setRequireOriginal` when `ACCESS_MEDIA_LOCATION` is granted, else Android strips the GPS position from what PhotoXT reads. This was the root cause of Phase 5 copies and moves of phone photos losing their location (found 2026-11-16). *Save* on a phone photo asks for the permission first.
- Copy/paste edits: `EditClipboard` holds one recipe (`filesDir/edits/clipboard.json`). Paste always takes the look (light, colour, detail, filter, retouch) and takes geometry, overlays and the frame only when ticked (`Pasting.merge`, over each photo's own edit). Batch apply is *Paste edits* on a grid selection. What depends on the photo is found again in each one by the job (`PhotoFinder`): its subject for a new background, background blur and subject masks, its faces for skin smoothing; the edit row keeps the recipe as rendered. Red-eye fixes are never pasted.
- Object eraser models (Robin, 2026-11-19): LaMa, MI-GAN and DeepFill v2, switched with chips at the top of the eraser panel (off while a model downloads or runs); the choice is `EditorSettings.eraserModel` (synced), MI-GAN by default. All three are trained on Places2 (scenes) and work at 512 px. LaMa is big-lama (Apache-2.0, 104 MB) from `Dineshsoudagar/big-lama-512-LiteRT`; MI-GAN (MIT, 16 MB) from `litert-community`; DeepFill v2 (8.7 MB) is built by `models/deepfill_v2.py` and downloads from raw.githubusercontent.com at commit 89c3daf (pushed 2026-11-20). Each downloads on first use, resumes, is checked against its pinned size and SHA-256, and is saved as `<model>-<SHA-256 prefix>.tflite`, so files of older pins are pruned at the next download check; Settings deletes them all. GPU delegate first, CPU after, and the log says which ran; a model the phone's GPU couldn't build gets a `.cpu` marker beside its file, so later loads skip the GPU (deleting the models clears it).
- Colour picker: Android 17's `Intent.ACTION_OPEN_EYE_DROPPER` (the colour comes back in `Intent.EXTRA_COLOR`); on older versions, or when the dropper can't open, the colour is picked from the photo.
- The editor is always dark, whatever the app's theme. Its history keeps 100 steps; a slider's drag is one step, recorded when the finger lifts.
- Crop's *Custom* ratio is typed as width:height (`3:2`, `3x2`, `1.91/1`), 1:10 to 10:1, and kept as `Geometry.customRatio`.
- detekt: `CyclomaticComplexMethod` ignores simple `when` entries (an enum mapped to one label or call each), since the editor's 15-tool tables tripped it everywhere.

- Module added in Phase 8: `feature/collage` (the studio, Library → Collages). The model is in core/model `Collage.kt`; layouts, geometry, the renderer and the export are in core/render (`CollageLayouts`, `CollageGeometry`, `CollageRenderer`, `CollageExport`), and the export job is in core/transfer `Collages.kt`. No new libraries.
- Collage model (`CollageProject`, JSON through `CollageJson`): a slicing layout tree (`LayoutNode`, weights) for grid, smart, stitch, shapes, story and before/after, and free placements for freeform. A cell holds its photo, the framing (focus, zoom, rotation, flips) and an optional look (an `EditRecipe` holding only the look). Templates are generated (rows, columns, hero, centre, two big, spiral) and kept only when every cell's ratio is between 1:3.2 and 3.2:1. That gives 100+ in all across 2–20 photos (18 for 9).
- One renderer, `CollageRenderer`, draws both the studio's preview (Compose's canvas) and the export (a software bitmap). A cell's look runs through the editor's shader (`LookPass`). Smart layout: justified rows or columns by linear partition over the photos' aspects, with the focus moved to keep detected faces in.
- A stitch takes its layout from its photos' shapes at draw time; the geometry ignores the stored weights. A swap or a new photo therefore never crops one, and a stitch has no dividers to drag. It exports at the narrowest photo's own width, never enlarged (65,000 px at most).
- The export is a COLLAGE transfer job: render, write, decode back (the check), and place with MD5.
  - *Delete sources* adds TRASH jobs for the shown photos only. They are inserted in the same Room transaction that marks the collage DONE, so nothing reaches the Trash unless the collage verified.
  - Undo (snackbar, or Transfers) turns them into RESTORE jobs, and the collage stays.
  - The Drive write scope for the trash accounts is asked for first (`JobProgress.scopeAccount`).
- Collage memory: the export shrinks the collage to fit free memory rather than fail. Caps: 8K long edge and 33 MP, so "8K" of a square is 5,760 × 5,760.
- Drafts live in Room v8 (auto-migration 7→8, table `collage_project`), saved 0.8 s after each change, with their pictures in `filesDir/collages`; Library → Collages lists them. The studio's history keeps 100 steps; a gesture is one step.
- Make collage: timeline selection → More, 2 or more selected, opening with 2–20 photos (videos left out), oldest first. It is not offered in the Hidden list.
- Shapes are an outline (heart, circle, hexagon, letters) that clips the whole collage. Before/after uses the first two photos. The studio is always dark, like the editor.
- The studio's controls (`ChipRow`, `SliderRow` and the rest, in feature/collage `Controls.kt`) are copies of the editor's, marked `ponytail:`. Move them to core/designsystem when a third screen needs them.
- The studio's screen talks to its view model through `CollageStudio`, so `CollageScreenshotTest` (app tests) draws it with a stand-in.
- detekt: `TooManyFunctions` ignores Hilt `@Module`s too (one provider per DAO).
- MediaStore trashing is an update, not a delete, and the trashed item drops out of every default query. The quick index pass (after a MediaStore change) therefore asks for items trashed since the last generation and drops them (`MediaStoreReader.trashedSince`). Before this, PhotoXT's own Delete left the photos showing until the app came back to the front (found on the A15, 2026-11-25).

- The eraser models' phone check (`EraserModelsTest`, core/ml androidTest): install `core/ml/build/outputs/apk/androidTest/debug/ml-debug-androidTest.apk` and run it detached with `am instrument -w -r -e class com.photoxt.core.ml.EraserModelsTest com.photoxt.core.ml.test/androidx.test.runner.AndroidJUnitRunner`. It downloads the three models (129 MB), fills a hole over a red sign in a made-up sky with each, logs load and run times under EraserCheck and the processor under Eraser, and leaves the pictures in `/sdcard/Android/data/com.photoxt.core.ml.test/files/eraser-check/`.
- Eraser models on the A15 (2026-11-20, `EraserModelsTest`, six runs): MI-GAN on the GPU, 0.5–1 s an erase (2–4 s with loading); DeepFill v2 half on the GPU (221 of 411 operations) and half on the CPU, 6.4–9 s (8.5–12 s with loading); LaMa on the CPU only, 11–19 s (13–20 s with loading), because the A15's Mali GPU can't build it (OpenCL kernel compile error, then "Batch size mismatch" in the OpenGL fallback); that failed try cost 28–40 s at each load until the `.cpu` marker. Every fill was within 1–4 levels of the sky around it. MI-GAN's raw output outside the hole is tinted (the same on the cloud's CPU); only the hole is used.
- Phone access without WPSC: the Cowork device shell (a Linux VM on robin-laptop) reaches the phone over the LAN. Download platform-tools for Linux there, `adb pair <ip:port> <code>` from the phone's *Pair device with pairing code*, then `adb connect` to the *IP address & Port* on the Wireless debugging screen. The VM's adb server dies with each call, so every call starts it and connects again (a three-line wrapper in the VM's home). mDNS doesn't reach the VM, so the ports come from the phone's screen, and a new VM pairs again. The WPSC issuer was refused by the cloud session's safety check every time on 2026-11-19 and 2026-11-20.
- The phone moves between two Wi-Fi networks (192.168.0.103 and 192.168.0.250); each move turns Wireless debugging off, and the old mDNS entries linger.
- Test faces with no real person behind them: NVIDIA's StyleGAN sample of 15 generated faces (`stylegan-teaser.png` in NVlabs/stylegan on GitHub, reachable from the cloud workspace).
- Wireless adb can drop to about 0.4 MB/s and break off on big transfers (`failed to read copy response: EOF`) while shell commands still work; a 70 MB install then won't finish.
- Gradle 9 fails a test task that discovers no tests, and Hilt generates test sources in every Hilt module, so each such module needs at least one test.
- Cloud workspace: the full CI (Lint across every module plus Robolectric) needs about 6 GB of swap (`fallocate -l 6G`, `mkswap`, `swapon`), or the Gradle daemon is killed. The swap file is gone after a workspace restart.
- WPSC from a cloud session: run the staged issuer in place (`python3 -I <staged WindowsPowershellControl>/Server/wpsc.py run --dir … "…"`); it reads its credentials beside it. Copying the credentials elsewhere was refused.
